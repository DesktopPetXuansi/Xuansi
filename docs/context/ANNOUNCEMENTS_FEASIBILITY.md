# 软件端官方公告可行性分析

## 状态与结论

2026-11-16 核验范围：桌宠与独立官网工作区的相关源码、GitHub 参考项目的公开源码及说明。桌宠源码基线为 `464763e`，官网源码基线为 `32e6fff`。本报告是可行性分析与路线建议，尚未冻结修改方案，未实施功能、运行功能测试、部署或发布。

已确认的产品范围以[决策记录](DECISIONS.md#软件端官方公告)为权威来源。2026-11-17 已确认下文的首版行为，实施与验证见[公告修改方案](ANNOUNCEMENTS_PLAN.md)。本文件保留前期研究证据、路线比较、成本和技术风险。

**推荐扩展现有官网管理后台与 Go API，由原生 Qt 软件端异步读取公开公告，本机保存已读及提醒状态。** 客户端实现借鉴 Prism Launcher 的异步订阅与缓存，管理端借鉴 Nextcloud 公告中心的权限、公告生命周期与通知分离。无需为当前需求引入完整通知平台或实时连接。

这条路线在技术上可行，现有项目已有必要的界面、网络和后台基础；主要工作在可靠同步与交互细节。结论来自静态代码核对，不代表已通过原型、容量或安装验证。当前没有发现必须更换技术栈的阻塞。

## GitHub 参考项目分析

按“原生客户端公告接收”“公告发布管理”“实时通知替代路线”筛选，而非按 Star 数排名。下列链接为本次查阅的分支源码，未来可能变化；本轮没有复制第三方代码或安装这些项目。

### Prism Launcher：最值得参考的客户端模式

[仓库](https://github.com/PrismLauncher/PrismLauncher) · [NewsChecker.cpp 源码](https://github.com/PrismLauncher/PrismLauncher/blob/develop/launcher/news/NewsChecker.cpp)

`reloadNews()` 检查是否已有加载任务，随后通过 `NetJob` 发起缓存请求；完成后读取订阅文件，以 Qt XML 解析条目，通过信号通知界面成功或失败。它体现了异步获取、请求去重、磁盘缓存、条目解析与 UI 更新分离。

适合借鉴这些职责划分。玄司已有 JSON API，建议采用结构化 JSON 表达等级、发布状态和修订信息，不必为了模仿参考项目增加 XML 订阅链路。所查文件并未提供本项目需要的后台草稿、撤回同步、本机已读及气泡提醒状态，不能将其视为完整公告系统。

文件标注 GPL-3.0-only，并包含上游版权说明。本路线只参考设计，独立实现；若后续决定复制代码，应另行核对对应文件许可及分发要求。

### Nextcloud Announcement Center：最值得参考的管理模型

[仓库及维护说明](https://github.com/nextcloud/announcementcenter) · [APIController.php](https://github.com/nextcloud/announcementcenter/blob/main/lib/Controller/APIController.php) · [Manager.php](https://github.com/nextcloud/announcementcenter/blob/main/lib/Manager.php) · [路由](https://github.com/nextcloud/announcementcenter/blob/main/appinfo/routes.php)

控制器在发布、删除和通知管理操作中检查管理员资格；管理层保存公告，再关联接收组，按选项投递通知队列并发出发布事件。它把公告正文和通知行为分开处理，删除公告时也清理关联通知。接口还支持定时发布等参数，但这些并非玄司基础档需求。

值得借鉴：公告是持久内容，气泡只是提醒；发布和撤回必须维护通知状态，不能只修改列表。其用户组、评论、邮件及 Nextcloud 框架依赖与当前匿名桌宠公告不匹配，直接部署整个应用会引入额外平台。README 明确说明维护投入有限；源码标注 AGPL-3.0-or-later。本轮采用设计参考，不建议直接引入应用。

### Gotify：可行的实时方案，但与已选时效不匹配

[仓库及 README](https://github.com/gotify/server) · [API 契约](https://github.com/gotify/server/blob/master/docs/spec.json)

官方说明提供 REST 消息发送、WebSocket 接收以及用户、客户端和应用管理。API 区分发送应用令牌与接收客户端令牌。它适合自建实时推送；当前需求允许分钟级到达且无需登录，引入后还要处理身份映射、连接恢复和桌宠 UI，并补齐公告草稿、预览及撤回语义。

本轮核验到 README 和 API 契约，没有完成其传输层源码审查。仓库说明使用 MIT 许可。建议保留为未来确有秒级推送需求时的候选，首版不采用。

### Novu：适合复杂消息中心，当前范围偏重

[仓库及能力说明](https://github.com/novuhq/novu) · [无头 Inbox 使用方式](https://github.com/novuhq/novu/blob/next/docs/platform/inbox/headless-mode.mdx)

官方资料展示了通知工作流、多渠道投递、偏好、消息列表和已读操作；其现成 Inbox 主要面向 Web 集成。原生 Qt 客户端仍需编写界面与状态适配。对于当前只有公开官方公告、没有个人通知或跨设备同步的需求，这些能力无法抵消新增平台的集成与运维成本。

本轮仅核验官方说明与使用文档，未深入其调度内核。具体所选包和部署形态的许可边界待核实，不将整仓默认视为同一许可。首版不引入。

## 推荐路线与关键可行性

建议的数据流为：管理员在现有官网后台编辑并发布 → 服务端保存公开公告及发布状态 → 桌宠匿名获取 → 本机更新缓存与未读状态 → 原生列表展示，重要公告择机提醒。用户不需要打开网页阅读公告。

### 发布内容与客户端状态分离

建议服务端维护公告身份、标题、正文、等级、发布状态和时间；本机分别维护已读与已提醒状态。显示气泡不等于用户已经阅读，打开详情才标记已读。重复拉取同一公告不应重置这两种状态。字段和接口尚未冻结。

正文建议首版支持文字、标题、列表、加粗和 HTTPS 链接等有限格式，配合编辑工具栏和预览；不开放任意 HTML、脚本、附件或远程图片。这样能降低后台预览与 Qt 显示差异，并避免公告变成执行入口。此项为建议默认值，用户若需要图文公告，需要重新评估图片存储、加载与离线缓存。

公告应来自受控官方地址；匿名请求不携带聊天内容、模型密钥或账号凭据。公告中的“更新”仅引导到既有更新中心，公告正文不能指定程序执行、安装命令或覆盖更新信任根。Qt 对链接协议、重定向及内容长度应做独立限制。

### 拉取、缓存与撤回

约五分钟轮询可以满足当前时效选择。启动检查和手动刷新应共用进行中的请求，避免重复并发；定时检查加入小幅随机偏移，失败后退避，恢复后补取。后台检查失败只更新状态，不持续弹窗。网络异常不应清空有效缓存或阻塞聊天与桌宠动画。

建议使用 ETag 条件请求减少未变化内容的传输，并区分 304、有效新内容、无效响应。缓存按官方来源隔离。历史公告分页读取，不在每次轮询下载全部历史。

**撤回不能只靠“最新列表中消失”。** 老公告可能已经不在首页，但仍在本机缓存。接口必须能表达撤回状态，或提供可校验的有效集合；如后续使用增量游标，游标过期必须允许完整重新同步。具体协议留待修改方案比较并冻结。

撤回在下一次成功同步后移除正文及待提醒项，可留下“已撤回”的状态标记。离线设备无法即时得知撤回，应显示缓存及最后同步时间；已经展示或被用户复制的内容也无法远程追回。后台发布页需要让发布者理解这个边界。

### 提醒与既有桌宠行为

公告气泡需要可点击、可关闭、不自动抢焦点；用户点击后打开原生详情。不要把公告正文送入 AI 生成或语音播放链路。普通公告保持安静，重要公告分别记录提醒状态，重启后也能去重。

出现多条重要公告时建议聚合提示，防止断网恢复后连续弹出。静默、全屏或忙碌期间建议保留未读状态，等待合适时机再提醒；具体产品规则见下节。实际呈现与本机状态落盘之间无法用一个跨 UI/磁盘事务保证绝对“只显示一次”，异常退出边界需选择并测试，不能承诺严格恰好一次送达。

## 首轮提出的产品建议

以下为 2026-11-16 报告提出的建议及权衡。后续确认结果见[决策记录](DECISIONS.md#软件端官方公告)。

| 项目 | 建议 | 取舍 |
| --- | --- | --- |
| 首次安装遇到旧公告 | 历史可查，但不逐条触发旧气泡；首次成功同步作为提醒基线，后续新公告正常提醒 | 避免初次打开被历史消息打扰，但新用户不会收到旧重要公告的气泡 |
| 静默、全屏或忙碌 | 保留红点，气泡延后；恢复后合并提醒一次，多条消息仍可逐条阅读 | 尊重现有陪伴体验，气泡出现时间可能晚于公告拉取时间 |
| 已发布内容更正 | 草稿可编辑；发布后锁定正文与等级，更正时撤回并发布新公告 | 规则简单且提醒身份明确，但改错字也需重新发布 |

路线建议同时假设首版采用上述有限文字格式。若需要图片或发布后原地修改，应在冻结方案前提出；后台展示和缓存一致性的工作量会随之变化。

## 成本与容量估算

估算假设：一名熟悉 Python/Qt、Go 及现有前端的开发者；沿用现有管理员登录、数据库和部署；正文采用有限格式；不包含新增需求、正式发布等待或用户验收等待。以下为人工工作量估算，不是已执行结果或工期承诺。

| 工作领域 | 粗估人日 | 不确定性 |
| --- | --- | --- |
| 服务端公告状态、匿名读取、权限与审计、缓存契约 | 1.5–2.5 | 撤回同步协议与现有迁移组织 |
| 后台草稿、编辑预览、发布撤回与历史管理 | 1–2 | 编辑器与 Qt 格式一致性 |
| 客户端列表详情、读取缓存、已读与可点击提醒 | 2–3 | 气泡交互、静默仲裁、窄窗布局 |
| 接口集成、故障验证、安装包和回归准备 | 1.5–2.5 | 离线撤回及异常退出边界 |
| 合计 | 6–10 | 修改方案冻结后再细化 |

新增基础设施预期可保持在现有服务范围内，但实际生产剩余容量待核实。轮询平均请求率约为在线客户端数除以 300：1,000 台约 3.3 次/秒，10,000 台约 33.3 次/秒；每台持续在线一天约 288 次定时请求，另加启动和手动刷新。此计算不含重试、分页与集中启动峰值，不是服务器承载能力证明。

ETag 能减少响应体，仍然存在请求和可能的服务端查询成本。应缓存公共公告结果，避免每次无变化检查都进行昂贵查询；量级显著增长后再评估 CDN 或静态清单。当前在线规模、公告频率、现有数据库余量均未实测。

## 风险与后续验证标准

| 风险 | 验证应证明什么 |
| --- | --- |
| 匿名接口暴露草稿或撤回正文 | 未发布内容不可通过列表、详情、缓存响应获取；普通用户无法管理公告 |
| 缓存残留已撤回公告 | 已缓存的旧分页内容在同步后也失效，重启或长时间离线恢复不会重新弹出 |
| 重复提醒或误标已读 | 轮询、重启、重复响应不反复提醒；气泡关闭不自动标记阅读；多条合并后状态可解释 |
| UI 卡顿、资源竞争 | 请求在后台进行，聊天和动画正常；静默与全屏下行为符合确认结果 |
| 气泡点击穿透改动影响现有体验 | 公告能点击到正确详情，原聊天气泡与拖拽不回归，不自动抢焦点 |
| 网络与数据异常 | 超时、断网、304、畸形内容、过大响应、错误游标均保留有效状态并可恢复 |
| 富文本与链接风险 | 预览和客户端显示一致，不能加载脚本、本机文件或任意协议 |
| 兼容与发布顺序 | 新客户端遇到尚无接口的服务端可降级；旧客户端继续正常运行；公告不触发未授权安装 |

修改方案阶段再给出准确的模块边界、接口、持久化方式、变更顺序及验收用例。不能把上表视为测试已经通过。
