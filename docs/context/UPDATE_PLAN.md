## 状态与范围

2026-11-14 整理并开始实现。首版产品范围与恢复边界已确认。已建立独立启动器的版本选择、签名清单检查、下载缓存、版本包解压和事务状态内核，以及只读健康探测；Qt 控制中心已加入更新页、偏好、手动入口、稍后提醒和跳过版本，并能在重启后识别已下载的完整包。独立官网仓库已加入清单字段与迁移。本机专用签名密钥已生成，私钥位于仓库外且仅当前用户可访问，离线备份待用户完成。已从提交 `8f668b7` 编译 `0.9.1` 桥接安装器，构建并本地签名完整版本包；签名、哈希、解压及随包健康探测已通过，隔离夹具覆盖健康成功提交和失败恢复。真实安装、旧版数据升级、故障注入及线上发布仍未完成。当前更新页仅在已接入新版布局的安装副本中启用；尚未发布部署。已确认决定以[决策记录](DECISIONS.md#自动与手动更新)为权威来源。本文件维护功能方案、参考证据、工程问题和验收条件。

目标：安装版用户能够手动检查并安装新版，也能够按偏好自动检查、下载和在退出时安装，升级保留记忆、配置和已下载模型。

第一版已确认范围为 Windows x64 Inno 安装版、稳定渠道、完整程序包更新，支持取消和续传；商店更新、差分补丁和模型自动升级暂缓。源码运行与商店包应识别分发方式并提供对应指引，不执行 Inno 覆盖升级。灰度发布建议暂不纳入。

更新失败自动恢复上一版本为用户明确要求，取代先前仅提供修复入口的建议。技术路径为版本目录隔离、独立启动器、持久化事务及启动健康确认；隔离夹具已验证关键路径，实际安装环境仍需验证。

现有[更新中心原型](../prototypes/update-center.html)只作为交互参考，模拟状态不代表功能完成；取消和续传已纳入首版，原型中的暂停等具体交互仍需落实与验收。

## 功能与技术方案

采用 Qt 更新中心、官网版本入口、版本隔离及独立启动器。Inno 保留为首次安装、旧版接入和修复入口；日常更新由独立协调器在未激活目录准备新版，再通过健康确认切换版本。现有直接覆盖程序目录的方式不再作为日常更新主路径。

### 用户操作

- 控制中心和托盘提供手动检查，显示当前及目标版本、更新说明、包大小、进度、结果和可操作错误。
- 自动检查默认开启，建议启动后延迟执行，此后每 24 小时一次；离线或失败退避，不重复打扰。
- 自动下载默认关闭；开启后后台下载并验证，不代表允许立即中断会话安装。
- 默认由用户确认“安装并重启”；提供“退出时安装”选项。建议仅在应用内正常退出时兑现，系统关机、崩溃和强制结束时推迟到下次运行。
- 支持稍后提醒、跳过此版本和取消下载；手动检查不受自动检查开关限制，并可重新显示跳过的版本。
- 自动和手动入口共用状态机与互斥控制，只有一个检查、下载或安装任务。
- 第一版支持中断后续传；必须校验资源版本、ETag/Range 响应和最终完整文件，资源变化时重新下载。建议界面暂停复用取消传输但保留已验证分块的能力。

### 下载与信任

流程：查询候选 → 验证发布元数据 → 选择兼容且更高版本 → 下载缓存 → 验证文件 → 等待安装时机。

- 官网为客户端更新入口，GitHub Releases 保留同一份产物分发。下载文件由官网自身、对象存储还是 GitHub 承载，尚待部署核验；官网入口不等于安装包已在国内镜像。
- 使用 HTTPS、长度限制、SHA-256 和 Ed25519 签名。签名元数据绑定版本、渠道、平台、分发类型及包哈希；明确序列化方式、格式版本、有效期和密钥标识。
- 签名验证使用 Go 标准库 Ed25519 实现，不自行实现算法；发布公钥嵌入独立启动器。
- 更新信任根独立于可配置的资源平台地址；更新请求不携带模型 API Key、聊天数据或官网登录令牌。跳转与镜像仍需受控并验证同一产物。
- 首版正常网络更新拒绝降级；自动恢复仅能选择本机已记录且验证通过的上一成功版本，不能从服务器任意指定旧版本。过期、签名错误、不兼容的清单不进入安装。已签名旧清单重放、系统时钟异常和密钥轮换需测试及明确处理。
- 更新签名私钥不进入源码、安装包或下载服务器。它与 Windows Authenticode 代码签名不是同一能力，不能据此承诺消除系统发布者提示。

### 安装与恢复

- 安装前确认真实安装目录、分发类型、剩余空间和同目录实例；路径必须经过约束与校验。
- 持久化必要状态，停止本应用会话及相关子进程，等待文件释放后再升级。不按 `python.exe` 等通用进程名批量结束进程。
- 稳定启动器与协调器位于版本目录外，不依赖正在升级的 Python、Qt 或虚拟环境。建议采用小型原生 Windows x64 启动器（优先评估 Rust）；新增构建工具链及其维护成本需纳入实施方案，具体依赖尚未选定。
- 程序按版本保存在独立目录，各自拥有 Python 和依赖；当前版、上一成功版及准备中的新版不互相覆盖。不修改活动虚拟环境来准备新版。
- 新版在最终版本路径建立环境，检查完成前不激活。Python venv 通常不能直接搬迁，不能先创建后改名；见 [Python 官方说明](https://docs.python.org/3/library/venv.html#how-venvs-work)。程序包或锁定依赖必须具备完整可验证来源，先准备齐全才进入停机阶段。
- 共享模型和用户数据与版本目录分离；复用已有 `XUANSI_WRITABLE_ROOT` 能力前，核对 `runtime` 中可变文件与版本专属二进制，不能直接共用全部运行时文件。
- 保留模型选择、API 配置、凭据引用、记忆、人设和导入形象；已下载模型不重复下载。完整更新产物与首次安装 EXE 可分开生成，由同一构建快照、清单和签名绑定，官网不得把两种产物混选。
- 使用事务编号、上一成功版本、候选版本及数据兼容信息形成持久化记录。准备、试运行、提交、恢复各步先写可恢复状态再改变外部状态；使用受控的单写者锁、同卷文件替换和刷新，保留可校验的上一份记录。原子替换不能独自证明断电持久性，需故障注入验证。
- 状态路径为 `PREPARING → PREPARED → TRIAL → COMMITTED`；准备失败不动旧版，试运行失败进入 `ROLLING_BACK → ROLLED_BACK`。启动器先处理未完成事务再允许业务启动，旧版恢复不依赖网络。
- 新版首次试运行上限暂定 60 秒，显示升级验证状态，暂不接受聊天、录音、配置修改或其他业务写入。仅在事务绑定的本地握手确认版本、UI 事件循环、配置读取、数据访问及关键模块加载通过后提交；不以在线 API、模型下载或大型模型加载成功为条件。达标即可结束，不强制等待满一分钟；具体实现需通过慢设备实测验证该上限，不默默延长产品等待时间。
- 试运行失败时，停止确认为该事务创建的进程，恢复上一成功版本并自动启动，记录失败版本的版本号与产物哈希并暂停再次自动尝试，防止升级循环。无法释放锁时保留恢复状态，不破坏性清理；下次启动继续恢复。
- 断电时无法运行恢复程序；要求恢复供电后下一次启动由启动器自动完成恢复，无需用户找旧安装包。若系统仍运行且协调器存活，立即自动恢复。磁盘损坏、旧文件被外部删除等无法靠软件保证恢复的情况，应保护数据并提示修复。
- 第一版默认恢复目标为最近一次已通过健康检查的版本，正常保留一份已验证旧程序及依赖；准备下一次更新时可能短暂同时存在三份环境。只有新事务提交成功且不再引用时才回收更早版本，模型不随版本复制。

### 数据兼容与首次接入

- 必须区分恢复程序与恢复业务数据。试运行阶段冻结真实业务写入，结构迁移在一致性副本上验证，未提交时旧数据保持可用；数据切换与程序选择由同一事务记录关联恢复。
- 发布门槛要求前一成功版本能够读取新版正式运行后产生的数据，覆盖每一条支持的直接升级路径。升级成功后不会自动因普通崩溃回退；如执行另行授权的修复或回退，也不得覆盖用户新增聊天或记忆。破坏兼容的迁移须重新设计，不通过自动更新直接下发。
- 不能把“恢复旧备份”作为正式运行后的通用恢复策略，否则会丢失升级后的用户数据。备份一致性、凭据存储与非文件副作用均需核验；试运行禁止触发这些业务副作用。
- 第一版自动恢复覆盖准备/切换失败、首次健康检查失败和未提交事务中断。准备失败保持旧版；激活候选后失败自动恢复旧版。正式提交后的普通网络错误、正常使用崩溃和后续连续启动失败均不属于首版自动回滚范围，须保留诊断与修复入口。
- 现有 `0.9.0` 通过一次手动桥接安装接入新结构。原根目录环境不搬动、不覆盖，先建立独立候选环境，核对数据路径及快捷方式，再完成健康确认；桥接失败恢复旧启动入口。桥接是独立验收场景，不能假设旧版已具备新健康握手协议。
- 启动器自身不能随普通应用包覆盖；首版固定启动器协议。以后升级启动器需独立恢复设计及桥接发布，避免应用尚可恢复而启动器先损坏。

### 官网与发布

- 扩展现有发布元数据及契约，保持已有下载页面和旧客户端兼容；选包同时考虑渠道、系统、架构、分发类型和最低兼容条件。
- 先构建、签名并验证产物可下载，再公开更新清单；签名后的元数据修改必须重新签名。
- 记录版本、源码提交、产物哈希和签名标识，不记录私钥及用户秘密。
- 已确认采用本机受控签名、离线备份密钥；本机已生成密钥并仅用于本地候选包签名，离线备份待用户完成。需要发布自动化时再评估迁入私有仓库受保护的 CI 发布环境。
- 发布撤回只停止继续推送，不等于已升级用户自动降级。紧急修复优先发布更高版本；离线修复入口保留。

## 实施顺序与验收

1. 按已确认边界完成必要工程核验，冻结布局、数据兼容矩阵、健康握手、事务恢复协议、接口及签名格式。先完成技术设计与验证用例，不以文档整理代替实现授权。
2. 优先实现两个本地测试版本之间的独立启动器、持久化事务、健康握手和自动恢复；先验证失败闭环，再接网络更新。
3. 完成 `0.9.0` 桥接安装、版本专属 Python 环境、共享数据与模型路径、快捷方式和卸载行为。
4. 实现官网兼容接口、完整更新产物签名、下载、取消/续传、手动入口与状态机。
5. 接入自动检查、下载偏好、延后与退出时安装，完成本机签名和发布流程。
6. 在可回收的 Windows 环境做正常升级及逐阶段终止/断电模拟，核验自动恢复后可离线启动旧版且数据正确，再安排用户验收。代码完成、测试通过、安装验证、用户验收和发布分别记录。

验收条件：

- 旧安装升级后，记忆、配置、凭据引用、形象及模型路径保持正确；不触发不必要的模型下载或 API 能力验证。
- 同版本、旧版本、错误架构、不匹配分发类型与不兼容版本不安装；手动与自动并发只执行一个任务。
- 覆盖断网、取消、续传资源变化、包损坏、签名错误、过期清单、空间不足、实例未退出、安装子进程失败和重启失败。
- 实际 Windows 环境验证正常升级和自动恢复：逐阶段结束协调器、终止新版、模拟重启与记录损坏；恢复到记录的上一成功版本，配置和数据完整，不依赖下载旧包。
- 单独验证依赖安装失败、旧版环境保持完整、首个桥接版本失败、恢复中再次中断、空间不足和失败版本不被循环推送；并检查成功提交后新增业务数据不会被旧快照覆盖。
- 覆盖非相邻版本升级、睡眠/关机/主动取消、后台业务写入冻结、旧快捷方式、多实例和提交临界点中断；升级成功后普通崩溃不得误触发首版范围之外的自动回滚。
- 官网旧下载入口仍可用，未发布或已撤回版本不再作为候选；安装包与签名清单一致。
- 日志不含 Key、令牌或聊天内容；关闭自动检查后仍可手动检查。

开发检查沿用[操作手册](RUNBOOK.md#桌面客户端开发)中的 pytest/Ruff 命令，并按新增模块限定测试范围。官网后端、契约和发布检查命令需在实施时按对应仓库规则确认。
