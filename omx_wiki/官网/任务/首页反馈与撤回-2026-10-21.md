# 首页反馈、撤回与审核

2026-10-21，用户批准首页底部直接输入、匿名撤回、服务端防刷，以及审核后公开到 GitHub。沿用 PostgreSQL；当前应用未接入 Redis，不增加依赖。

## 数据与边界

- 正文、联系方式、公开许可、审核状态、撤回凭据摘要和持久限流均在 PostgreSQL。浏览器仅保存每条反馈的编号和随机管理凭据，提供带 fragment 的管理链接；凭据不进入 URL 查询、服务器日志或管理员响应。
- 所有新反馈先 `PENDING`，审核通过才入 GitHub 队列。旧收据继续返回 `NEW`，桌面提交协议兼容。旧记录通过迁移保留其既有投递状态，不补发。
- 撤回与审核/投递使用行锁协调。投递尚未开始时可撤回并清理正文、联系方式和诊断；已经开始公开投递时记为 `WITHDRAWAL_REQUESTED`，由管理员在 GitHub 清理后确认。公开前后不能使用相同的成功承诺。
- 管理凭据采用 32 字节随机值的 64 位小写十六进制，数据库只存 SHA-256。每条权限独立；缺失或错误凭据统一拒绝。
- 除既有内存限流外，数据库按访客 IP 的 HMAC 摘要持久限制每分钟 5 次、每小时 20 次；相同访客十分钟内重复内容不新增。幂等重试不消耗新额度。撤回单独限流，不占提交额度。

## 契约（在现有 `/api/v1` 下扩展）

1. `POST /feedback`：现有输入新增可选 `managementToken`；浏览器发送稳定 `Idempotency-Key`，失败重试复用相同编号、凭据和正文。收据仍为 `{id, createdAt, status: "NEW"}`。
2. `POST /feedback/{id}/management`：输入 `{managementToken}`，返回 `{id, createdAt, status, moderationStatus, githubIssueUrl, canWithdraw}`，不返回正文或联系方式。
3. `POST /feedback/{id}/withdrawal`：输入同上，返回同一管理视图。未公开则 `WITHDRAWN`；已经开始投递则 `WITHDRAWAL_REQUESTED`；重复操作幂等。
4. `POST /admin/feedback/{id}/moderation`：输入 `{decision: "APPROVE" | "SPAM" | "CONFIRM_WITHDRAWAL"}`，返回完整管理员反馈；发布仍需原作者公开许可、有效的既有渠道配置。确认公开内容撤回由管理员先完成 GitHub 清理。
5. 管理员反馈新增 `moderationStatus`、`publicConsent`、`githubIssueUrl`。审核状态为 `PENDING | APPROVED | SPAM | WITHDRAWN | WITHDRAWAL_REQUESTED`，与原有 `NEW | IN_PROGRESS | RESOLVED` 处理状态分开。

## 实施与验证

1. 先补数据库迁移、后端契约、撤回/审核的权限与并发回归，再实现接口和投递边界。
2. 首页末尾、页脚之前放内嵌反馈输入；正文必填、联系方式选填，公开确认默认不选；标题取正文首行最多 80 个 Unicode 字符。失败保留草稿，成功展示撤回和保存管理链接；提供不依赖登录的管理页。
3. 页脚与帮助入口定位首页反馈；管理员可审核、标垃圾、查看公开链接、确认已完成公开内容清理。
4. 隔离 PostgreSQL 跑完整后端、Python 反馈兼容回归；前端类型、lint、生产构建，真实 Chrome 验证首页直输、刷新后管理、错误留稿、撤回、审核及移动布局。仅使用合成数据，不发真实 GitHub Issue。

本轮只修改本地代码并验证；生产发布沿用项目既有发布流程，不将本机验证视为线上已更新。

## 本轮结果

本地实现完成，未部署、未向真实 GitHub 创建 Issue。反馈及临时防刷计数复用 PostgreSQL，不引入 Redis、依赖或新账号系统。公开前撤回会擦除正文、联系方式和诊断，幂等收据与审核状态保留；已开始投递的撤回申请由管理员清理后确认，运行中的投递禁止提前确认清理完成。任何 GitHub 仓库外送均需作者许可，私有仓库也不能绕过。

匿名管理链接将凭据放在 fragment；浏览器在发出提交请求前保存编号与随机凭据，数据库只保存摘要。损坏的管理链接明确报错，不回退另一条反馈。清除浏览器数据且丢失管理链接后不能自动证明匿名身份，需要管理员协助。数据库中的正文及联系方式不会被复制到浏览器持久存储。

当前防刷包含服务端每分钟 5 条、每小时 20 条的持久额度，十分钟同来源重复内容拦截，以及人工审核。无效请求另有较宽的进程内保护，管理操作独立限流。未接入外部人机验证服务，不能将这些保护描述为完全阻止分布式滥用。旧独立收件运行模式仍须通过连接同库的完整官网管理员后台审核，新反馈不会再自动公开。
