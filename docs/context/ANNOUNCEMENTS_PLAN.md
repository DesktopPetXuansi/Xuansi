# 软件端官方公告修改方案

## 范围

以[已确认决策](DECISIONS.md#软件端官方公告)为产品依据。管理员在现有官网后台保存草稿、预览、立即发布和撤回。桌宠在原生控制中心提供公告入口、未读状态、列表和详情。首版使用纯文本结构块表达段落、小标题、重点、项目符号及 HTTPS 链接。后台和桌宠根据块类型渲染文本，不解析用户提供的 HTML。

## 结构与顺序

1. 官网契约和发布闭环。新增独立公告表与全局修订号。草稿可编辑，编辑和发布校验草稿版本。发布、撤回及审计在同一事务内完成。公开接口按照修订号分页同步，每条公开记录携带正文或撤回标记。后台接口复用管理员会话和 CSRF。
2. 官网后台。沿用工作台布局与鉴权，提供草稿编辑、预览、发布确认、撤回确认及分页历史。发布和撤回后重新加载服务端状态。
3. 桌宠接收。启动、打开入口及运行中约每五分钟触发同步，共用进行中的请求。同步按官方源保存本机游标、最近成功时间、正文缓存及独立已读和提醒状态。首次完整同步建立提醒基线。后续同步消费撤回标记，即使公告在历史页也清除本机正文和待提醒记录。错误保留有效缓存。使用条件请求和有上限的响应读取。
4. 桌宠展示。原生公告入口显示红点，列表可分页查看本机缓存。打开详情标记已读。重要未读公告在可交互桌面提醒一次，静默、全屏或忙碌时延后。多条积压合并显示，单条气泡点击打开对应详情，多条气泡点击打开公告列表。公告气泡有独立关闭操作，按既有窗口管理规则显示。
5. 验证。官网核对迁移收集、管理权限、状态冲突、撤回内容隔离、分页和 304；运行 Go 测试、生成契约、前端类型检查和后台浏览器走查。桌宠覆盖首装、空基线后新增、延期、去重、撤回、异常响应和离线恢复；运行 pytest、Ruff 和 Qt 导航回归。最后用本地官网与桌宠联调发布和撤回。安装包、生产部署及用户验收单独记录。

## 同步契约

接口采用现有 `/api/v1` 和 `data` 封装。匿名 `GET /client/announcements?after=0` 返回 `changes` 与 `hasMore`，首个请求的游标为 0。每条变更有 `id`、严格递增的 `revision` 和 `status`。发布记录另含标题、等级、正文和发布时间，撤回记录只含该公告的身份、状态和修订号。服务端通过事务内更新单行修订号锁保证提交顺序。公告内容不可在同一 ID 下重新发布，因此每条公告只保存其最后一种公共状态。

每页最多 32 条，正文 JSON 编码后最多 20 KiB，客户端单页接收上限 1 MiB。客户端验证全部分页后原子提交缓存，提交成功才推进游标。只将空页 ETag 用于下一次相同游标的请求。服务端发现游标超出当前修订号时返回 409，桌宠从头同步并原子替换缓存。

提醒状态在气泡显示前落盘。异常退出恰好发生在两者之间时，气泡可能略过，该公告仍可通过未读红点进入。

数据库恢复验证边界：从旧快照恢复后，如果重新发布的修订号已经追平某个离线客户端，单凭数值游标无法检测历史回滚。这类恢复仍需让受影响客户端重新建立公告缓存基线。

管理员 `/admin/announcements` 提供分页读取和创建草稿。`PATCH /admin/announcements/{id}` 保存草稿，`POST /admin/announcements/{id}/publications` 发布，`POST /admin/announcements/{id}/withdrawals` 撤回。编辑或发布收到过期版本时返回 409。网页使用服务端校验作为权限和内容边界。

## 基线与执行边界

2026-11-17，官网原工作区的自动更新分支在 Goose 收集阶段因两个 `00013` 迁移复现 panic。公告官网代码从本地 `origin/main` 的独立工作树开始，公告迁移使用 `00016`。自动更新分支日后合入时需要为清单迁移分配新的唯一编号。桌宠以现有更新分支的 `464763e` 为基线，已有两项导航断言仍采用更新中心加入前的页数。校验时记录是否消除这两项基线失败。
