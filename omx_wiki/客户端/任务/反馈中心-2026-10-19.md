# 软件反馈中心

用户要求在软件中增加反馈中心。采用软件内填写和提交、网站后台私有接收的方案；已提供 GitHub 跳转的渠道备选问题，默认实施推荐方案，允许用户继续调整。沿用小控制中心，入口放在底部和托盘，不增加主标签。

## 操作与边界

- 填写类型（使用问题/功能建议/其他）、标题、说明，可选联系方式。
- 系统和版本信息默认不附带，勾选后可预览；只收集应用版本、系统、架构、Python 和 Qt 版本，不读取聊天、密钥、截图、录音、完整日志或用户目录。
- 点击提交后异步发送到当前连接的官网，无需登录；成功以服务端收据为准，网络失败保留草稿。重复提交使用同一请求编号，防止不确定回执造成重复记录。
- 管理员在网站“反馈中心”查看并标记待处理/处理中/已解决；反馈正文和联系方式不公开。
- 本轮先完成源码和本机链路验证；公开安装包与生产网站部署各自记录，不能将本地服务的成功当作公网已启用。

## 模块与契约

| 模块 | 职责 |
| --- | --- |
| feedback-data | 输入校验、固定诊断字段和可复制内容 |
| feedback-client | 同一 HTTP 会话取得 CSRF 后匿名提交；不读取官网授权或 AI 密钥 |
| feedback-ui | 保留草稿的轻量窗口、状态、预览、复制和明确提交 |
| feedback-service | 限流、限制请求体、校验、幂等持久化、私有管理员列表和状态修改 |
| feedback-admin | 网站管理入口、列表/详情和状态处理，复用现有会话鉴权 |

`POST /api/v1/feedback`：JSON 为 `category`（BUG/SUGGESTION/OTHER）、`title`（1–80字符）、`description`（1–4000字符）、`contact`（可省略，最多160字符）、`diagnostics`（可省略，仅appVersion/system/architecture/pythonVersion/qtVersion）。`Idempotency-Key` 为标准非零UUID；成功 `data={id,createdAt,status:"NEW"}`，id等于请求编号。正文不超过32KiB，仍走现有精确Origin与双提交CSRF。返回结构沿用现有API；只在数据库提交成功后返回成功。同内容重试返回原收据，确认后“再写一条”开启新编号。

`GET /api/v1/admin/feedback?status=NEW&limit=20&cursor=...`：管理员列表，`data`数组、`meta.nextCursor`；条目另含category/title/description/contact/diagnostics及updatedAt。`PATCH /api/v1/admin/feedback/{id}`仅接收status（NEW/IN_PROGRESS/RESOLVED），返回更新后的条目。普通用户、访客及资源Bearer不能读取或处理收件箱。

## 执行与验收

1. 固定契约，分别实现客户端、服务、后台视图；不新增运行依赖。
2. 验证空输入、重复点击、错误响应、旧站404、CSRF/权限、长度、幂等冲突、状态及分页。
3. 真实Qt在720×560控制中心及窄窗口核对入口，反馈窗口验证输入、诊断预览和失败草稿；独立Chrome验证管理员与访客边界。
4. 运行相关回归、完整源码检查与类型/构建检查，记录本地可用范围。
